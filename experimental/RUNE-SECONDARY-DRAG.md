# Rune secondary drag extension proposal

Pinned Rune b726a4d routes `secondary_down` and `secondary_up` through `crates/rune/src/runtime/input/secondary.rs`. The capture stores the original target and release is dispatched only if the release still hits that target. `El::on_secondary_press` is a completed context-menu action; `on_drag` is primary-only. `pointer_buttons` explicitly reserves secondary for context menus. Window and web input both call the same runtime methods, so a board-only application wrapper cannot observe the missing down or release events.

A maintainable upstream patch should add an opt-in `El::on_secondary_drag` handler using the existing `Drag` phase and cancellation model. Capture the registered element on secondary down, deliver down/move/up in its local coordinates even outside its bounds, and deliver a cancelled up when capture is lost, the window deactivates, the node disappears, or the runtime is torn down. Suppress `on_secondary_press` for this opt-in gesture, while preserving current context-menu and accessibility behavior for all other elements. Add runtime tests for cross-target movement, outside release, capture loss, and ordinary secondary menus, plus desktop and web adapter coverage.

EngineRoom can then register one handler on the board, map local coordinates through orientation to squares, store the origin and modifier-derived brush at down, show a temporary preview during move, and toggle a circle or arrow only on an in-board non-cancelled release. Clear the temporary gesture on navigation or FEN change. Tests must drive actual `secondary_down`, pointer movement and `secondary_up`, including flipped boards, all modifier combinations, outside releases and cancellation. User annotations remain separate from candidate engine arrows.

The patch belongs in a maintained Rune fork or upstream revision, pinned together with rune-kit and rune-theme-opencode. Vendoring the pinned Rune crate (about 17 MB including assets/tests), editing Cargo's shared git checkout, or patching only the native window adapter would create a fragile or inconsistent dependency and is intentionally not included here.
